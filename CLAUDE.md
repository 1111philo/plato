# CLAUDE.md

Project-level instructions for Claude Code sessions working on plato.

## Project overview

plato is an Open Source, AI-powered [microlearning](https://philosophers.group/platos-microlearning/) platform. Learners work through focused lessons in a continuous conversation with an AI coach, designed for completion in ~20 minutes.

- `client/` — React 19 + Vite SPA
- `server/` — Node.js + Hono, deployed as AWS Lambda (SAM)
- Brand: "plato" (always lowercase)

## Architecture

Quick map of the system. **Deep dives, incident history, and the *why* behind these invariants live in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)** — read the relevant section before changing one of these subsystems.

- Login required, all data server-side. JWT access (15 min) + refresh (30 day) tokens in localStorage (`plato_auth`); login accepts email or username. Unique editable `username` per user. `server/src/lib/sessions.js` owns sessions: `user.tokenVersion` (bumped on password/email change and reset) ends every other session; reset tokens never refresh; refresh rotation has a 30 s grace and the client refreshes once, ahead of expiry; sign-in, refresh, and reset are rate-limited. → [details](docs/ARCHITECTURE.md#sign-in-and-sessions)
- 2 Lambda functions (API Gateway buffered CRUD + Function URL streaming SSE for AI chat); 5 DynamoDB tables (users, invites, refresh-tokens, sync-data, audit-log).
- Content is `_system` sync-data (`prompt:*`, `lesson:*`, `knowledgeBase`, `settings`). Prompts are bundled in `client/prompts/*.md` and upserted on every server startup — admins can't edit prompts directly. Hot read-only paths read `_system` through a 30 s in-container cache (`lib/system-cache.js`; this container's `_system` writes clear it, other containers may lag ≤ 30 s); the lessons list sends parsed fields, not markdown; learner requests never scan users. → [details](docs/ARCHITECTURE.md#system-data-cache-scale) User-created lessons live under the user's sync-data (`lessons:custom-*`).
- **11 AI agents** (prompts in `client/prompts/`, each with an HTML header documenting reads/callers/purpose — stripped before sending, so it's documentation only and never changes behaviour): coach, assessor, claim-check, lesson-creator, lesson-owner, lesson-extractor, knowledge-base-editor, knowledge-base-extractor, learner-profile-owner, learner-profile-update, course-progress-update. Program KB + Lesson Catalog are appended to system prompts at runtime (`client/js/promptAssembly.js`, called by `orchestrator.js`); the KB is framed as background, and the coach's rules after its `<!-- AFTER CONTEXT -->` marker go after the KB and catalog, so they're the last thing it reads (#584).
- **Learner language (#240)** — every agent writes in the learner's browser language via `withLanguage()` (`client/js/language.js`); English adds nothing to prompts. The directive lists every parsed literal (tags, JSON keys, lesson headings, `- Can `) as keep-in-English — add any new parsed literal there too. → [details](docs/ARCHITECTURE.md#learner-language-240)
- **One open source model for all 11 agents** — `qwen.qwen3-vl-235b-a22b` (Apache-2.0), declared once as `LLM` in `server/src/lib/ai-provider.js`, mirrored in `client/js/api.js`, injected into plugins as `ctx.LLM`. **No per-agent routing.** Bedrock is the only backend (local dev included — the Anthropic API provider was removed). Non-Anthropic models require the **Converse API**: legacy `InvokeModel` doesn't reject them, it returns HTTP 200 with an OpenAI-shaped body, so callers silently read `undefined`. `server/src/lib/converse.js` translates between plato's internal Anthropic wire format and Converse. A replacement model must clear **four** bars: on Bedrock us-east-2 (UIC requirement), accepts images (learners paste screenshots), reliably emits plato's literal tags, and carries an **OSI-approved license**. That last one is a constraint, not a preference — plato is AGPL-3.0, so *open weight isn't enough*: Llama 4 and Gemma ship under non-OSI community licenses and are ineligible despite passing every functional check (Llama 4 Maverick measured faster and cheaper, and is the fallback only at the cost of that bar). **Prompt caching is Claude-only on Bedrock — don't add it.** `POST /v1/ai/messages` accepts only `LLM`, caps the payload, and limits each user (per container); errors are typed (`throttled`/`overloaded`/`timeout`/`rate_limited` with `retryAfterMs`) → [proxy limits](docs/ARCHITECTURE.md#the-ai-proxys-limits-451-scale-review). → [details](docs/ARCHITECTURE.md#ai-provider--model-choice), [why this model](docs/MODEL_SELECTION.md)
- **Conversation & image persistence** — chat history is one append-only `messages:<lessonId>` record; progress is a separate `lessonKB:<lessonId>`. **Images are never inlined in `messages:`** — each is its own compressed `screenshot:*` record, referenced by `metadata.imageKeys` (DynamoDB's 400 KB item cap; inlining base64 silently lost conversations, #191/#193). The `LessonChat` resume effect keys on stable values, never the `lesson` object identity. → [details](docs/ARCHITECTURE.md#image--conversation-persistence-191-193)
- **Behind this response (#411)** — each assistant reply can carry `metadata.agents` (`client/src/lib/agentActivity.js`: which agents ran, what they read, what they did — built from parsed tags, never raw model reasoning), shown by the `AgentActivity` disclosure on every chat. → [details](docs/ARCHITECTURE.md#behind-this-response-411)
- **Link attachments** — a learner can attach a web page to a coach message. It's fetched + read **server-side** (`POST /v1/links/fetch`); the page text is injected into the coach call on that turn only (image parity), and only `{ url, title }` is persisted in `metadata.links`. SSRF defense (`server/src/lib/url-guard.js`) is load-bearing — the server fetches user URLs from inside AWS. → [details](docs/ARCHITECTURE.md#link-attachments)
- **Lessons** — three statuses: `public`, `private` (visible to `sharedWith`), `draft` (admin-only, no markdown yet; true draft iff `status==='draft'` AND markdown empty). New lessons start as `draft`; "Create Lesson" flips `draft`→`private`. Editing is conversation-based (no raw markdown editor), deep-linked at `/plato/lessons/:lessonId/edit`, with a manually-refreshed markdown preview pane. An optional `## Coach Directive` section carries author-supplied runtime instructions for the coach (e.g. "reference the learner's project", "share this code") — extracted verbatim, parsed into `lesson.coachDirective`, and surfaced via `buildContext`; it never overrides completion semantics. Lessons are organized **Course → Unit → Lesson** (#408). Storage keeps pre-hierarchy names: **`_system:course:<id>` is a Unit** (`lesson.course` = unit id), **`_system:program:<id>` is a Course**; order lives in `_system:programOrder` (courses; Getting Started is always first) / `program.unitIds` / `unit.lessonIds` and only orders (stale entries fall back to name order) — see `server/src/lib/hierarchy.js` and [hierarchy details](docs/ARCHITECTURE.md#courses-units-and-lessons-408). Unit delete cascades `course:null`; course delete leaves units unassigned. Learners see lessons in that order (`client/src/lib/lessonOrder.js`); "next lesson" crosses units but never courses. A per-learner `courseProgress:<unitId>` record carries a tiny distilled note of what the learner demonstrated in a unit's *other* lessons — regenerated on completion by the `course-progress-update` agent (incremental, ~600-char cap) and injected into the coach context as `unit.progress` (the coach also gets `course.name`, the course above); informational only, never overrides completion. → [details](docs/ARCHITECTURE.md#course-progress-cross-lesson-memory)
- **Pacing & completion** — limits in `client/src/lib/constants.js` (MAX_EXCHANGES=11, MIN/MAX_OBJECTIVES=2/4, MINS_PER_EXCHANGE=1.8), mirrored in `server/src/lib/lesson-limits.js`; prompts use the literal numbers. **No hard cutoff** — lessons run until the coach awards `progress >= 10` **and every objective is checked off** (#584): on a turn where the coach checks off an objective or scores 10, the assessor agent checks the learner's own messages and must quote them; code throws out any quote that isn't the learner's (`client/src/lib/assessment.js`), and a 10 that isn't backed up is held while the coach asks for what's missing (`checkGrading`). If the check fails, nothing new counts and the lesson stays open (fail closed); on a second completing turn in a row it can't check, the coach's grading stands and it's logged, so no learner is stuck. On a held turn, a reply that still says the lesson is done is replaced (`claimsCompletion` patterns, then the `claim-check` agent for other wording), and a reply that writes the learner's answer for them is rewritten once before grading (`draftsForLearner`). Measure changes with `server/scripts/coach-eval.js`. Never auto-complete on exchange count. `extendedLessons` is informational only. Post-completion the thread is feedback-only — `progress` and `activitiesCompleted` both freeze in code (not just via prompt instruction, which is model-dependent), while KB updates keep flowing; scores are clamped 0–10. `applyCoachResponseToKB` (`lessonEngine.js`) is the single owner of completion semantics. The sync route refuses a lessonKB write that *transitions* to `completed` unless `messages:<lessonId>` holds the coach's opener (S5; the KB lands before the turn's messages, so no learner message can be required). A coach reply that arrives without its tags is re-asked for them (`recoverMissingTags`), never guessed from its prose. The lesson overview's objectives checklist ("N of M objectives met"; `objectivesMet`, one-way, `client/src/lib/lessonWork.js`) is informational and never completes a lesson. → [details](docs/ARCHITECTURE.md#pacing--completion-philosophy)
- **Denormalization** — derived activity fields (`lessonsCompleted`, `lastActiveAt`) are denormalized onto the user record with a **single writer** (`applyActivityEffects` in `server/src/routes/sync.js`), transition-detected (no double-count), best-effort. Underlying sync-data stays the source of truth. **All dashboard/per-user KPIs count only published (public) lessons** — drafts, privates (even when shared), and custom lessons are excluded from numerator *and* denominator (`server/src/lib/lesson-visibility.js`); a completion counts iff its lesson id maps to a public `_system:lesson:*`. The `?include=stats` user-list recomputes `lessonsCompleted` per request and heals the counter (visibility can't be derived from the stored count alone). Per-user stats (#136) and Admin dashboard KPIs build on this. → [details](docs/ARCHITECTURE.md#denormalization-policy)
- **Custom user fields (#364)** — admin-defined profile fields (text, textarea, dropdown, link, phone; optional or required). Definitions in `_system:settings.userFields`; values on the **user record** as `customFields` keyed by stable field id (so the Users list can search/filter without extra reads). `server/src/lib/user-fields.js` is the single validator. Per-field `hideFromLearner` (admins only) and `hideFromApi` (not on public forms or the wait-list API); learner/public routes pass their list as `editable`, so hidden values are kept, never dropped. Required fields are collected by `ProfileCompletionGate` around the classroom routes — status fetched fresh each load, **fails open**, client-side only, not enforced at signup. → [details](docs/ARCHITECTURE.md#custom-user-fields-364)
- **Names (#402)** — users have `firstName` / `lastName` (last name optional); `name` is kept, always derived, for plugins, audit, emails, and rollback. `server/src/lib/names.js` reads every request (a lone `name` is split at the first whitespace) and shapes every response (`nameFields`). `nameSource: 'auto'` marks an inferred split the UI invites people to correct. Migration `m005_name_split`. → [details](docs/ARCHITECTURE.md#first-and-last-names-402)
- **Single sign-on (#401)** — sign in with an institution's account or with plato's password; both stay. **Core owns it** (`routes/sso.js`, `lib/oidc.js`, `lib/external-identity.js`: flow, account rules, session); a plugin only supplies a provider (`auth.provider`; `plugins/entra-sso` for Microsoft Entra). Trust settings (tenant, client id, secret, owned domains) are **deploy-time template parameters, never admin settings or committed values**. Invite only: SSO never creates an account without an invite. No tokens in URLs (one-time code + cookie). Accounts made by SSO have no `passwordHash`. Auto-linking by email removes the password and ends sessions unless the account's email was proven (`emailVerifiedAt`; clear it whenever an email changes). Connecting, disconnecting, and password reset are credential changes (current password; reset drops the link). An admin can style a provider's button (icon + background/text colors, plugin settings); core validates it for every provider (`lib/sso-button-style.js`: hex pair with ≥ 4.5:1 contrast; PNG/JPEG/WebP data URL ≤ 20 KB, no SVG, no remote URL) and serves only what passes. → [details](docs/SSO.md)
- **Wait list (#363)** — public `/waitlist` form and `POST /v1/waitlist` (open list, or a Bearer API key for outside forms). Entries are `invites` rows with `status: 'waitlist'`, no ttl, and a `profile`; config is `_system:waitlist`, not settings. Admin invites from Users → Wait List; signup fills in the entry's answers. → [details](docs/ARCHITECTURE.md#wait-list-363)
- **Invites expire but are kept** — an email invite's link works 7 days (`expiresAt`, not DynamoDB `ttl`), then shows "Invite expired" and keeps the person's details until Resend (single or bulk) gives a fresh link. Never put `ttl` on an email invite: DynamoDB deletes it and a wait-list person's details with it. Link invites keep `ttl`. `server/src/lib/invite-expiry.js`, migration `m006`.
- **Data migrations** — any change to existing stored data ships as an append-only entry in `server/src/lib/migrations.js`: runs once per install on cold start, additive/idempotent/conditional, never rewrites learner work, and must stay rollback-compatible with the release being upgraded from (Beta-RC-232). Gate: `server/tests/migrations/upgrade-from-rc232.test.js` (runs RC-232's own handlers on migrated data); dry-run with `server/scripts/migrate.js`. → [details](docs/ARCHITECTURE.md#data-migrations)
- **Roles (#435)** — admin, educator, learner (stored `user` before; `normalizeRole`), tester (read-only everything). `server/src/lib/permissions.js` maps roles→permissions and every `/v1/admin` route→permission; **unmapped routes are admin-only** and a test fails if a route isn't mapped. `authorize` middleware enforces; the client mirrors the map (`client/src/lib/permissions.js`, kept in sync by test) for nav/controls only. → [details](docs/ARCHITECTURE.md#roles--permissions-435)
- **Notifications (#388, #389, #400)** — automated and admin-sent email goes through `server/src/lib/notifications.js`. It covers editable templates, multipart raw MIME with one-click unsubscribe, opt-outs in the server-only `notify:state` record, and `EMAIL_ALLOWLIST`, where empty means no one off prod. **Every automation ships OFF**; the invitation emails (`invite`, `account-invite`) are always on and editable, and ignore the allowlist like before. Every send first checks SES's account-wide bounce/complaint list (`lib/email-suppression.js`, fails open) and returns `{ suppressed }` instead of sending; admins only ever see plato's own addresses on it. The waitlist confirmation sends only from the request that created the entry, so it never sends twice. Messages go to everyone (any role), chosen roles, a group, or specific people; messages stored before `allRoles` keep reaching learners only. → [details](docs/ARCHITECTURE.md#notifications-388-389-400)
- **Admin "View as User"** — read-only learner-classroom audit via `?asUserId=<id>` on GET `/v1/sync*` and `/v1/lessons*`; writes never carry the param (403 server-side + client throw). Session-granularity audit log. → [details](docs/ARCHITECTURE.md#admin-view-as-user)
- **Trace mode (#595)** — a learner's opt-in, readable record of everything behind one conversation: Start trace / Stop trace in the lesson panel's **Data Trace** tab (beside Overview, opened from the "Overview (N of M Objectives)" header button) or in Learner Profile's Trace (`preferences.traceScopes`, per lesson or `profile`). No account-wide switch and no admin Trace (not in View as User, not for authoring chats). Records are the user's own `trace:<scope>:<t|b|p>:<id>` sync-data, kept out of the bulk `GET /v1/sync` and listed with `?prefix=`; never on `messages:`. `POST /v1/ai/messages` with `trace: true` returns the server-only facts (real model, region, applied settings, reasoning, the provider's own error with AWS identifiers removed). **Off must stay a strict no-op**: byte-identical requests and responses, nothing written. In the UI the tab and dialog are "Data Trace" and the word is otherwise "Trace"; "audit" means the audit log. **The view derives, it doesn't guess or restate**: each call records its agent's whole header, its `stage`/`check`, and each result names its `call`; rules are worked out from recorded values at view time (`traceView.deriveRules`), so a fix corrects old traces too; numbers and tag names come from the step that used them (`client/tests/trace-readable.test.js` fails otherwise). Plugins report their own lesson-start work (plugin API 1.7.0): a traced `lessonStarted` call gets a per-call recorder (`ctx.trace`, plus a recording `ctx.ai`), and the host cleans and bounds the steps (`server/src/lib/plugins/trace.js`) and returns them as `pluginTraces`, never inside `enrichments`. → [details](docs/ARCHITECTURE.md#trace-mode-595)
- **Observability** — errors flow `server/src/lib/logger.js` (snake_case `code`) → `GET /v1/admin/logs` (merges ring buffer + CloudWatch, aggregates by `code`) → pilot report + log-watch alarm. **Before adding any error detection or alert, read [`docs/OBSERVABILITY.md`](docs/OBSERVABILITY.md)** (the three-tier model + decision guide).

## Plugins

Manifest-driven plugin system modeled on VS Code/Vite/WordPress. Plugins live in `plugins/<id>/` and are bundled into the SAM build (no runtime code uploads — Lambda's read-only FS). The admin UI at `/plato/plugins` toggles activation and configures plugins.

- Host code: `server/src/lib/plugins/` (registry, manifest, hooks, lifecycle, sdk), `client/src/lib/plugins/` (`<PluginSlot>`, loader, SettingsForm). Types in `packages/plugin-sdk/index.d.ts`. Docs in `docs/plugins/` (README, AUTHORING, AGENTS, EXTENSION_REFERENCE, CAPABILITIES, API_VERSIONING, EXAMPLES, schema, templates). Scaffolder `scripts/create-plato-plugin.js`; CI gate `scripts/validate-plugins.js`.
- **Anti-goals (plugins MUST NOT):** override completion semantics (`applyCoachResponseToKB` is the single owner), introduce hard exchange-count cutoffs, write `_system:settings.*` directly, read/write another plugin's settings, mount routes outside `/v1/plugins/<id>/`, modify files outside their own `plugins/<id>/` folder.
- **When changing the plugin contract:** bump `PLUGIN_API_VERSION` in `server/src/lib/plugins/version.js`, update `docs/plugins/plugin.schema.json` enums, `packages/plugin-sdk/index.d.ts`, and `docs/plugins/EXTENSION_REFERENCE.md`. `docs/plugins/CAPABILITIES.md` is the source of truth for documented vs. implemented.
- **Trace mode:** a plugin that hooks `lessonStarted` must call the AI through `ctx.ai` and send outbound requests through `ctx.trace.fetch` (or `ctx.trace.record`), so its work shows in a Trace; `client/tests/transparency.test.js` fails otherwise. Recorders are per call — never module-level state.
- **Tests:** core plugin tests alongside each plugin (`plugins/<id>/server/*.test.js`); host tests at `server/tests/lib/plugins/*.test.js`.

## Deploy

Full procedure, SSM parameters, environments (prod / playground), CloudFront, and backups are in **[`docs/DEPLOY.md`](docs/DEPLOY.md)**. Automation (deploy dispatch, the agentic workflows, branch protection, versioning) is in **[`docs/AUTOMATION.md`](docs/AUTOMATION.md)**.

- Prod (`plato` stack) auto-deploys on push to `main`; playground (`plato-playground`) on push to `playground` — both via `repository_dispatch` to the private fork. Merges to `main` auto-deploy to prod with live users.
- CloudFront → Lambda Function URL: the Origin Request Policy **must** be `AllViewerExceptHostHeader` (Function URLs reject mismatched Host headers).
- CloudFront also **must** send the origin custom header `X-Plato-Origin-Verify` = SSM `/plato/<stage>/origin-verify`; the server 403s anything without it (`server/src/middleware/originVerify.js`), so the Function URL and API Gateway URL can't be called around the WAF. `off` disables it (installs without CloudFront).
- The SAM build does not bundle the client — the `cp` steps for `client-dist` (SPA) and `client-content` (prompt seed files) are required; see `docs/DEPLOY.md`.

## Conventions

- **Accessibility is required**: every interactive element must be keyboard-operable, show visible focus (the global `*:focus-visible` rule in `client/src/index.css`; don't add `outline-none` without a replacement ring — `e2e/tests/focus.spec.js` checks), reflow at 320 px (`e2e/tests/reflow.spec.js`), and have an accessible name (aria-label, aria-pressed, role, etc.). Chat log uses `role="log"` `aria-live="off"`; new-message announcements go through a separate auto-clearing `role="status"` region; a streaming `AssistantMessage` is `aria-hidden` AND drops its `data-chat-message`/`tabIndex` so focus and Alt+Arrow nav can't land on an aria-hidden node; persisted messages carry sr-only speaker prefixes + `data-chat-message` for Alt+Arrow nav (`useChatKeyboardNav`). The inline `ComposeBar` (when pinned) is `inert`, not `aria-hidden`, so a focused control inside it is blurred rather than hidden-with-focus. `ComposeBar` sends on Cmd/Ctrl+Enter by default; the learner's `sendKey` preference can make plain Enter send (Shift+Enter = newline), and a visible hint (the textarea's description) says which. During a reply the composer stays editable (`sendDisabled`, not `disabled`), so learners can draft the next message (#247). Coach replies show as they stream in, with no typing animation → [details](docs/ARCHITECTURE.md#composing-and-showing-replies-247)
- **Always commit and push after changes.**
- **PR workflow for collaborative iteration**: open PRs as **Draft** (`gh pr create --draft`) while iterating interactively; mark Ready (`gh pr ready <n>`) only when the user says it's ready. If a Ready PR gets more iteration, convert it back (`gh pr ready <n> --undo`). Every push to a Ready PR triggers the full CI suite (Bedrock auto-review, CodeQL, lint ×2) — micro-commits there are noise and waste budget. Does NOT apply to plato-pilot PRs (opened Ready by design) or one-line bugfixes already approved up front.
- **Docs & tests**: update both alongside every code change (open-source project).
- **Getting Started stays current (#443)**: any PR that changes learner-facing behavior (controls, labels, chat behavior, completion, navigation) updates the Getting Started lesson that teaches it (`client/prompts/lessons/getting-started*.md`, three lessons in the bundled "Getting Started with plato" course) in the same PR. Use the real control names, and check the coach against the change with a real Bedrock run. Unedited copies on every install update themselves on deploy; edited copies get an "update available" notice → [details](docs/ARCHITECTURE.md#getting-started-the-bundled-orientation-course-443)
- **Dialogs** (`components/ui/dialog.jsx`, `alert-dialog.jsx`) cap at the viewport height and scroll (`max-h-[calc(100dvh-2rem)] overflow-y-auto`), so a long dialog never runs off-screen (#421). Don't remove that cap on a single dialog; if one needs an inner scroll area instead, override `max-h` on that dialog. **AdminLayout** has a skip link and `<main id="main-content">`. The list pages in `WIDE_PAGES` (`/plato/users`, `/plato/lessons`) drop the `max-w-4xl` cap so their tables show every column (#385); forms keep it.
- Admin pages (`/plato/*`) are never themed with classroom branding. Auth pages use `usePublicBranding`; classroom pages use `BrandingProvider`. Admin nav order: Home, Lessons, Users, Notifications, Customizer, Plugins (the Course → Unit → Lesson structure lives at Admin → Lessons → Courses & Units, `/plato/lessons/structure`).
- Footer text: "Powered by plato." (with period, with GitHub link). Emails use classroom name/colors from settings with that footer.
- API responses for user groups use `{ userGroups: [...] }` consistently (custom user fields mirror it: `{ userFields: [...] }`). User-created lesson IDs start with `custom-`. `loadLessons()` merges system lessons (`/v1/lessons`) with user sync-data lessons.
- Favicon: defaults to plato's; generated dynamically (logo on rounded-rect with primary color) when an admin uploads a logo.
